# BioCraft Master Admin — architecture and implementation blueprint

**Review-only; no administrative privileges or shared-project changes authorized.** This is an implementation plan, not a completed panel. No user-facing admin UI, production API, deployment, identity, live telemetry or content mutation exists. The included schema SQL is an exact *foundation proposal*, not the complete migrations for all modules; operation-specific functions, adapters, idempotency, reporting, onboarding and infrastructure migrations still need to be written and reviewed. Do not run either this SQL or the older prototype on the shared project. See [API contracts](master-admin-blueprint/API_CONTRACTS.md), the [SQL proposal](master-admin-blueprint/001-private-foundation.REVIEW.sql), and the [detailed test plan](master-admin-blueprint/TEST_PLAN.md).

## 2. Isolation recommendation and decision gate

**Safest target:** a genuinely separate Preview backend with independent database, Auth users/sessions/MFA, API keys, Edge deployment, Storage, configuration, analytics and logs. A separate Supabase project is the simplest boundary to reason about but is prohibited without explicit approval. An isolated Supabase database branch may isolate database contents but does not automatically prove isolation of every service or secret; verify the provider's actual branch capabilities, plan, Auth, functions, Storage, lifecycle, billing and credentials before treating it as strict isolation. Creating a branch is not authorized by this blueprint and may conflict with the previous prohibition on database duplication. No subscription or custom environment changes are proposed.

Preview Vercel frontend must use only the isolated Preview backend's publishable key, with trusted server-side credentials held only in that environment; Production remains unchanged. Configuration should fail closed if the backend identity is unexpected; client-facing URL alone is not a security boundary. No service-role key is shipped in a `VITE_` variable or browser; any narrowly scoped server secret remains server-only. Avoid shared privileged functions, users, data, telemetry or content; preview fixtures are synthetic and do not duplicate production data without approval. Maintain separate admin principal allowlists. No Production publication, merge, project creation, Preview env modification or administrator provisioning is authorized.

**Under current restrictions, real end-to-end Preview isolation cannot be completed** using the shared database. Local disposable tests can continue without a new hosted project. Any change to this restriction, new infrastructure or specific migration requires a separate explicit user decision. A Vercel Preview URL is not backend isolation. Even an approved UI must not target Production for testing.

## 3. Architecture and security boundaries

A lazy-loaded, noindex `/admin` application with independent auth/session client sits alongside—not around—the existing public guest shell. Static Preview build gate and noindex shells prevent accidental exposure; frontend gating alone is not security. Admin APIs sit behind a gateway, validate provider JWT and AAL2, and call narrow DB functions using the caller token. A non-exposed `bc_admin` schema stores membership, workflow and aggregate data; clients have no direct privileges. Each RPC checks enabled membership and named permission inside its transaction. PostgreSQL definer functions need a specifically reviewed least-privilege owner, explicit grants and fixed `search_path`; inspect owner bypass and direct PostgREST access. No generic SQL/table mutation endpoint. Keep the existing guest client, grants and RLS unchanged.

Use MFA for all staff, short sessions with documented expiry/logout and verified reauthentication for sensitive actions. The exact session maximum, current-session revocation, provider capabilities, recovery and account onboarding are release blockers. Proposed first Super Admin: independent verified identity and MFA enrollment, owner-controlled bootstrap on the isolated backend, separate exact approval, transactionally recorded; never ask for passwords or keys in chat. Protect the last enabled Super Admin and log membership changes. Auth directory queries/account actions require a separately designed restricted server adapter; do not expose service-role keys or blindly trust Auth metadata.

The model includes earlier requested **Analyst** as well as Super Admin, Admin, Editor and Moderator. Permission intent: S all including membership and security; A content approvals/publication and operations except roles; E draft and submit scoped content; M moderation/rejection, not publication or roles; Analyst only approved aggregate/report reads. Exact permissions are in [API contracts](master-admin-blueprint/API_CONTRACTS.md); capability UI is only a convenience, with tests for direct API/DB bypass. No raw user-generated content is sent to analytics.

## 4. Module-by-module specifications and gaps

All modules below are **not implemented or tested end-to-end**. Each write requires the transaction/review rules in §5, an isolated backend and a separately approved rollout.

1. **Dashboard:** typed cards for record counts and independently sourced user/visitor counts, rolling day/week/month charts, top content/platform, redacted recent activities and health. Source names, sample counts, timestamps and unavailable states are mandatory. Real-time updates only where provider and authorized data subscriptions are proven; otherwise bounded polling. Dependencies: read APIs, metrics pipeline, health adapter. Acceptance: unavailable sources never render zero/fake charts; filters/accessibility and freshness tested.
2. **User management:** list actual Auth accounts only, search/filter keyset paging, minimal authorized fields, explicit activity sources, account status and session action through provider-supported server adapter. Existing guest visitors are not accounts and cannot be listed as users. Roles belong to private membership, never client claims; last-super-admin and self-escalation protections, step-up and audit. Dependencies: chosen Auth model, directory API permissions, privacy policy, session/recovery design. Acceptance: ordinary users denied all admin operations; moderator cannot escalate; race test last-S protection.
3. **Bio management:** search/filter, stable pagination, EN/HI/Hinglish, create/edit/archive, category association, exact vs normalized duplicate warnings, bounded bulk preview/per-item outcomes, import/export with formula-safe CSV handling, approval, public preview, rollback-as-new-revision. Validate every field and cross-field consistency (`plain_content`, `emoji_rich`, `is_styled`, `style_type`); `character_count` is generated, not a writable input. Resolve `source_slug` and public collection path; no destructive hard-delete absent explicit policy. Publish updates guest data only when authorized, reviewed, conflict-free and switch enabled; current bundled fallback can show stale results during outages. Acceptance: duplicate races, invalid language, every platform length, concurrent edits, guest only sees published active data and fallback semantics.
4. **Categories:** draft name, unique slug, visibility/order/platform, SEO metadata and references; sanitize slugs and validate conflicts/redirect decisions before approval. Categories have no SEO columns; coordinate with `seo_pages` and static shell build. Archive rather than cascade-delete bios; retain URL/SEO continuity. Acceptance: collision, reorder, inactive children and route/canonical regression tests.
5. **Platforms:** retain all eight current platforms and tool mappings; editable reviewed settings only after public consumers read the approved version. Validate platform-specific counting units and limits separately; LinkedIn headline vs About distinct and English-only support reflected honestly. No generic fallback silently overwrites a platform. Acceptance: all eight, supported tools, languages, labels, counts, unavailable fallback and nonregression.
6. **Generators & libraries:** schema-versioned, typed configuration/templates tied to actual 12 registered tools, language and emoji controls, Unicode/font/symbol mappings and reversible release history. Generation is currently client-side rule-based; telemetry is opt-in aggregate only, quality judged by validated rules, not fictional AI or output quality. Runtime consumer changes need safe known-good bundled fallback and release atomicity. Acceptance: matrix of supported platform/tool/language combinations; output validity, Unicode grapheme edge cases, load time and no unsupported provider claims.
7. **Content & SEO:** typed homepage/landing sections, announcements, featured collections and metadata, drafts with safe preview. No arbitrary HTML/script or unreviewed external media. SEO needs route-specific build-time shell metadata/canonical/robots, not a DB-only update; preview build/validate then owner-approved release and confirm CDN/build before marking published. Dependencies: safe template schema, asset pipeline and media scanning, public integration. Acceptance: canonical, noindex, XSS, route snapshot, rollback, build failure and cached bundle fallback.
8. **Analytics:** explicit consent/privacy decision before instrumentation. Store only approved aggregate events: platform/tool identifiers, bounded timing bins and coarse interval; never search strings, names, generated text, bios, credentials or raw IP. Daily/weekly/monthly aggregates use UTC or labeled timezone, defined sample counts and small-cell suppression; unavailable data stays unavailable. No distinct-visitor count without a reviewed measurement design; client-side generation cannot be counted without instrumentation. Lab and actual field Core Web Vitals are separate, `p75` only when eligible real samples exist. Export via limited auditable jobs with safe CSV escaping and retention. Acceptance: privacy scan, opt-out, under-threshold suppression, metric reconciliation, timezone windows, no false realtime/field results.
9. **Security center:** MFA/step-up, membership lifecycle, session controls, server RBAC, read-only audit viewer, privileged change review and alert integration. Audits contain actor, action, target, request ID, reason, time and revision IDs; avoid secrets and personal content. Successful mutation and audit in one DB transaction; failed requests require a separate security log because a rolled-back transaction cannot persist its own audit. Owner can tamper with DB-resident logs; independent protected export required before claiming tamper-evidence or immutability. Acceptance: forgery, revoked user, expired/AAL1, role matrix, direct RPC, self approval, replay, audit durability and incident tests.
10. **System settings:** typed site/feature flags and safe maintenance announcement. A real maintenance mode must be explicitly designed around guest availability and separately approved, with default off and emergency restoration. Cache invalidation, backup/restore and error-monitoring controls are disabled until a compatible provider adapter, authorization, retention and test evidence exist. No invented backup success. Acceptance: kill switch, fallback, restore drill in isolated environment, cache version invalidation, secret and log leakage tests.

## 5. Data model, migrations and release flow

Exact foundation SQL: [001-private-foundation.REVIEW.sql](master-admin-blueprint/001-private-foundation.REVIEW.sql). It proposes **seven** private tables, all RLS-enabled with explicit restrictive deny policies and no `anon`/`authenticated` privileges:

| Table | Responsibility | Index/constraint highlights |
| --- | --- | --- |
| `bc_admin.members` | roles and enabled flags keyed by Auth UUID | role check, Auth FK, PK |
| `bc_admin.safety_controls` | publish and telemetry kill switches default off | singleton check/PK |
| `bc_admin.documents` | typed logical target identity/current revision | kind/external key unique, same-document revision FK |
| `bc_admin.revisions` | versioned draft and review payload | unique revision number, parent belongs to same document, authors/reviewers differ, state checks, indexes |
| `bc_admin.publication_history` | immutable-intent release linkage | revision and previous revision same document, unique published revision, index |
| `bc_admin.audit_events` | bounded redacted successful-action log | append-only mutation triggers; time and actor indexes |
| `bc_admin.metric_rollups` | approved aggregate buckets | metric/time primary key, non-negative samples, index; telemetry switch off |

The SQL is **foundation only**: it provides no permission functions, idempotency storage, resource validation, audit APIs, counters ingestion, read/publish adapters, session revocation or migration-safe operational ownership. `payload_sha256` is a supplied value; hashing, verification and canonicalization are not enforced yet. `publication_history` has no append-only trigger; only audit table does. Generic kinds do not create referential integrity for corresponding public rows. Retention, audit externalization, privacy dimension constraints and separate exact role-management/permission schema are still outstanding. The SQL defaults closed; do not treat schema constraints alone as permission enforcement. New migration files for these missing pieces, along with exact grants and rollback, must be drafted, tested and reviewed before approval. Existing 0001–0004 and all guest policies remain unchanged.

Workflow: validated draft → immutable submitted revision → independent approval or rejection → locked publish transaction with complete baseline/version comparison, same-transaction audit and history. Revise rejected change as a new draft. Rollback is a new draft from a historical version against the current base; it is independently reviewed and published, not an unaudited hard reset. Add a durable idempotency store so retries cannot duplicate events. Resource-specific adapters use static SQL for each table; generic JSON is validated by versioned schemas, not interpolated. Site/SEO release additionally requires a successful approved build before publication is declared. The switch starts off; consent/owner gates cannot be represented by UI hiding alone.

[099-schema-removal.REVIEW.sql](master-admin-blueprint/099-schema-removal.REVIEW.sql) is explicitly destructive: deletes the seven new tables and audit history, not production public data. No `CASCADE`; dependencies cause failure. It does not reverse live publishes, Auth changes or revoke tokens. Before any rollback: stop writes, preserve and validate an encrypted authorized backup, review data-retention obligations and dependencies, approve removal; recovery requires an independently tested restore and separate permission for public content. Operational containment should revoke affected new APIs and disable publish while retaining evidence; exact API-specific SQL depends on functions not yet written. All such actions are prohibited on the current shared DB.

## 6. Design and performance specification

Responsive accessible SaaS shell: collapsible sidebar, keyboard-operable navigation with current-page semantics, overview cards showing real source/staleness, table controls, descriptive labels, confirmation dialogs with focus management, empty/loading/error/permission states, system/light/dark theme with contrast checks, reduced-motion support. 320–767 mobile drawer/cards, 768–1023 compact sidebar, 1024+ expanded navigation; test 390, 768 and 1440 px plus keyboard/screen reader. No screenshots are claimed. Avoid placeholder buttons that imply unsupported capabilities.

Use route-based code splitting for admin modules and chart/export dependencies; debounce search, cancel superseded requests, keyset paginate/filter server-side, bound chart and batch sizes, cache only non-sensitive data by user/permission/version with short TTL and invalidate after mutation, disable browser/intermediary cache for sensitive responses. Add indexes based on representative `EXPLAIN (ANALYZE, BUFFERS)` in isolated fixture and verify plans at realistic scale; do not assume the included indexes solve all workloads. Use Web Workers for heavy CSV parsing and aggregate UI work; support virtualized tables where measured. Track request counts, payload, event-loop long tasks and Core Web Vitals; retain previous targets p75 INP ≤200 ms, LCP ≤2.5 s, CLS ≤0.1 as goals, not achieved claims. Lab Chromium is not real Android/field proof.

## 7. Verification and threat controls

**Local evidence:** `npm run test:admin-blueprint` creates an ephemeral PGlite fixture, verifies seven restrictive policies, client denial, representative guest-only RLS, constraints, default switches, audit triggers and destructive schema removal in fixture. `npm run test:admin-draft` covers the older narrow prototype and mocked gateway, not this v1 API. Both use simplified local fixtures and are not real Supabase security proof. `npm run typecheck` and existing collections/diagnostics tests were run previously; rerun in the implementation phase.

**Mandatory tests, not yet executed:**
- Security: anon, ordinary user, each role, disabled user, AAL1/AAL2, expired/wrong audience/signature tokens, copied/revoked sessions, forged role metadata, self-promotion, last-S races, self approval, direct PostgREST bypass, service key scanning, RLS/grant diff, definer search path, SQL injection and idempotent replay.
- Workflow: invalid platform/language/length and derived fields, duplicate/import races, transactional audit rollback, unauthorized mutations, author/reviewer separation, concurrent base conflicts, archive vs delete, rollback-as-draft, kill switch default-off, cache/SEO release failure, guest visibility and bundled fallback.
- Integration: all eight platform/tool/language combinations, actual Auth/MFA/Edge JWT provider, authorized account lifecycle, telemetry opt-out/suppression/no PII, quota/timeout/retry handling, monitoring and backup/restore, keyset pagination under concurrent changes.
- Quality: keyboard/axe, mobile/tablet/desktop, device/browser, load and query plans, long tasks and real Android field performance. Test accessibility, results freshness, failures and unavailable statuses; collect genuine screenshots only after a working UI exists.

Threats include account compromise/token replay, XSS and CSRF, elevated definer ownership, privileged API bypass, unreviewed content, log tampering, export leakage, unsafe SEO/content injection, race conditions, analytics re-identification, outage/fallback inconsistencies and privileged abuse. Corresponding mitigations require AAL2/recent step-up, validated JWT, scoped sessions, CSP/origin controls, DB permission checks, two-person review, append-only local audit plus approved external retention, privacy-preserving events, strict type validation and isolated restore drills. Constraints in SQL and local unit tests are not an independent security assessment. No privileged operation should be enabled before independent review and live isolated-stack tests.

## 8. Roadmap, dependencies and estimates

Rough planning ranges, not delivery commitments: assume one experienced full-stack engineer, part-time security review and product owner availability, and an authorized isolated backend. Unknown provider capabilities, UI review and integration complexity can increase these ranges.

| Phase | Work and exit criteria | Rough effort |
| --- | --- | --- |
| 0 | Decide isolation/privacy/scope, verify provider capabilities and backups, establish threat model, approve exact environment | 3–7 engineer-days plus approvals |
| 1 | Final exact migration series, least-privilege roles, Auth/MFA, bootstrap and full transactional audit/idempotency; test isolated Postgres/Supabase | 10–20 days + security review |
| 2 | Accessible admin shell, session handling, permission matrix, role/user directory adapter, audit viewer | 10–20 days |
| 3 | Bio and categories, public-read propagation, bulk validation and safe draft/review/publish/rollback | 15–30 days |
| 4 | Platform, generator/library, collection and UI/content/SEO integrations, all existing tools/eight platforms/languages | 20–40 days |
| 5 | Privacy-approved telemetry, dashboards/reports, real health and operational adapters, backup/restore drills | 15–30 days |
| 6 | Threat review/remediation, full automated/E2E/a11y/device/load testing, evidence and owner Preview approval | 10–20 days |

Some phases may overlap; dependencies, real user account requirements, independent audits and plan features may change scope. Do not total these as a guaranteed schedule. Key dependencies: isolated backend decision; verified Auth/MFA/session capabilities; permissions and four-eyes policy; content release/SEO strategy; privacy and analytics consent/retention; backup support and external audit retention; platform counting behavior; and explicit owner approvals.

## 9. Required decisions before activation

1. Authorize an isolation path consistent with project/duplication restrictions (or accept that a connected isolated Preview is blocked); do not create one until authorized.
2. Decide whether user management means staff only or future public registered accounts, what moderation applies to, and which data may be stored.
3. Approve telemetry consent, definitions, retention and small-cell suppression; otherwise analytics remain unavailable.
4. Agree detailed permission matrix, reviewer independence, MFA/session policy and owner-controlled first-admin onboarding.
5. Review final complete migrations/API implementation and isolated test evidence, then separately approve exact migrations, privileges, bootstrap and any publish. This blueprint is not that approval.
