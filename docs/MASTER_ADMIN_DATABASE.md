# Admin database candidate

Four locally tested **candidate** forward migrations are in `admin-backend/migrations/`; explicit reverse scripts for disposable synthetic fixtures are in `admin-backend/rollback/`. They are not in shared `supabase/migrations`, not deployed, not approved for the shared provider environment and not a complete backend. The owner selected existing project only; see [current shared-project boundary](MASTER_ADMIN_SHARED_PROJECT.md). Apply 001, 002, 003, then 004 only to a locally disposable synthetic fixture; reverse 004, 003, 002, then 001. The 001 reversal refuses nonempty tables; never use it to erase actual audit/data. 002 reversal removes integrity protection and is suitable only in an isolated test.

Tables: `admin_users`, `admin_roles`, `admin_permissions`, `admin_role_permissions`, `admin_user_roles`, `admin_sessions`, `admin_audit_logs`, `admin_settings`, `admin_drafts`, `admin_approvals`, `admin_content_versions`, `admin_publication_jobs`, `admin_notifications`, `admin_backup_records`, `admin_security_events` (all in `bc_admin_v1`). FKs, unique keys, constraints, indexes, immutable evidence triggers and RLS exist. The 003 candidate seeds eight role definitions and a proposed permission catalog, but no user memberships, provider functions or public target are created. Catalog rows alone are not authorization. Version payload hashes are length checked but not recomputed. Fields/states do not alone implement workflows, data protection, retention or audit completeness. Current model supports one immutable approval decision per draft; rejection requires a new draft. Account role transitions, first/last super-admin locking, unique resource mapping, typed validation, audit outbox, idempotency, server-granted operations and real target receipts are outstanding. See [progress](MASTER_ADMIN_PROGRESS.md) before use.

004 adds private draft creation, own-draft listing, submit and review with permission/session checks and atomic success audit. It grants no EXECUTE to clients. SQL `auth.uid()`/`auth.jwt()` must only be trusted when a verified request context cannot be spoofed; the tests deliberately mock these functions. A secure function owner, last-super-admin guarantee, fresh step-up, idempotency, denial-event sink, platform validation and actual API remain outstanding.
