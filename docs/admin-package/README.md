# Master Admin — technical review package (not applied)

**Status: partial implementation package; NOT approval-ready or complete.** This contains executable local prototypes, an inventory and an architecture / threat analysis. It does not implement the complete Master Admin Panel, and it is not safe to deploy to the shared project. In particular, the only content prototype is an existing-bio edit workflow; there is no complete CRUD, import/export, searchable revision or audit API, role-management API, integrated UI, full field validation, analytics, SEO, tools, platform, collection, generator or library management. No migration, policy, Auth account, function, guest permission or content was changed in the shared project in preparing this package.

## Files and exact proposed objects

- `010-bio-workflow-DRAFT.sql`: independent, transactional prototype. Creates schema `biocraft_control`; four tables, three indexes (in addition to primary-key indexes), four restrictive RLS policies, five helper functions and five public RPCs. It never alters existing guest policies or direct grants, and it initializes a database-owned publish switch **off**. Its *unexposed* schema and no client grants are important: all privileged access goes through narrow definer RPCs with explicit role/AAL checks. A schema and its policies/functions still affect the shared project and API even when only Preview uses them. Detailed table definitions, checks, foreign keys, indexes, function bodies, grant/revoke statements and policies are in the SQL file. No policies grant access to `anon` or `authenticated` for any admin table. RLS is enabled but not forced; table/function owner bypasses RLS, so functions are the security boundary. No untrusted client gets direct table or schema access.
- `020-bootstrap-SUPERADMIN-DRAFT.sql`: optional, separate owner-run first-member procedure, requiring a pre-existing user UUID and an empty member table. It records bootstrap atomically in the audit table. Requires separate approval and a trusted account verification procedure. `psql` variable is supplied locally, never in chat. The process does not create an account or verify MFA enrollment itself: the owner must independently confirm account identity, control, email verification and AAL2 enrollment before any approved use. Later role administration, audit and recovery are not yet implemented.
- `admin-gateway-DRAFT.ts`: illustrative Edge Function forwards only explicitly allowed operations, validates the token through Auth, passes the original caller token to PostgREST and uses a publishable key, never a service key. The database rechecks membership and `aal2`; CORS is not authorization. Deploy with verified JWT enforcement, one exact allowed origin, and approved configuration only. It is mock-tested locally, not deployed or tested in Deno/Supabase. Direct RPC calls can bypass this gateway, making database authorization mandatory. There are no read APIs, rate limits, production-grade error classification or security headers beyond those shown.
- `090-containment-DRAFT.sql`: disables the switch and revokes RPC execution; preserves records. This is a shared permission change and requires approval except where an independently authorized incident response procedure applies.
- `099-destructive-rollback-DRAFT.sql`: drops the five public RPCs and schema **including all new membership, revision and audit data**. It does not reverse content publishes or Auth sessions. It is deliberately labeled destructive and requires a separately approved retained backup and explicit deletion authorization. `DROP ... CASCADE` must be reviewed for dependencies created after deployment before any use.
- `../admin-drafts/001-readonly-rbac.sql`: earlier mutually independent read-only experiment, **not** a prerequisite and should not be applied alongside this prototype by default. It proposes `biocraft_admin_private.members`, plus context/dashboard functions. It has a separate local test and is not part of `010`'s object inventory.

### Table inventory

Existing public tables, unchanged: `bios`, `captions`, `categories`, `emoji_collections`, `fonts`, `generators`, `hashtags`, `platforms`, `seo_pages`, `symbols`. `auth.users` is an existing Supabase-managed table, not a new or modified table. Other system schemas are out of scope. Existing migrations 0001–0004 document application schema; live catalog inspection confirmed these ten public tables with RLS, guest/authenticated active-row SELECT policies, and no authenticated INSERT/UPDATE/DELETE privileges.

Proposed by 010:

| Table | Purpose | RLS policy for anon/authenticated | Special restrictions |
| --- | --- | --- | --- |
| `biocraft_control.members` | UUID, role, enabled status | `members_deny`: restrictive ALL, `USING(false) WITH CHECK(false)` | No direct grants; Auth FK; role CHECK |
| `biocraft_control.settings` | Singleton publish kill switch, off by default | `settings_deny`: same denial | No authenticated setting toggle |
| `biocraft_control.bio_revisions` | Existing-bio snapshots, author/reviewer and state | `bio_revisions_deny`: same denial | FK restrict, state and author/reviewer constraints, indexes |
| `biocraft_control.audit_events` | Append-only security event records | `audit_events_deny`: same denial | No client grants; update/delete/truncate triggers; timestamp index |

Restrictive policies are paired with *no permissive policies*, hence default deny. A superuser/table owner can bypass RLS and can alter the triggers or functions, so no claim of absolute immutability is justified. Only the five explicit RPCs are granted to `authenticated`, not to `anon` or PUBLIC. All five check current membership and MFA (`auth.jwt()->>'aal' = 'aal2'`) and role inside the database, regardless of gateway or client UI. SQL names and exact object definitions are in `010`. Prototype role capability is deliberately limited:

| Operation | Super Admin | Admin | Editor | Analyst | Ordinary Auth / guest |
| --- | --- | --- | --- | --- | --- |
| Create/update/submit own existing-bio draft | yes | yes | yes | no | no |
| Approve/reject another author's submitted draft | yes | yes | no | no | no |
| Publish approved draft from another author | blocked by default switch | blocked by default switch | no | no | no |
| Direct admin table access or guest-table writes | no | no | no | no | no |
| Read dashboard/drafts/audit, change roles | not implemented in 010 | not implemented | not implemented | not implemented | no |

The reviewer and publisher can be the same person but must differ from the author. The prototype snapshots only content, language, active/featured status and platform identity. Publishing locks the revision and bio, compares snapshot values, and writes the content plus an audit event transactionally. An approved switch enabling it would require its own database-owner action; no API enables it. **Do not enable it:** content writes currently leave `plain_content`, `is_styled`, `style_type`, and `emoji_rich` potentially stale; platform-specific limits, duplicate conflicts, SEO/public effects and complete rollback are not handled. Concurrent changes to fields outside the snapshot are not detected. The prototype is insufficient for production and fails the original completeness requirement. The default-off switch is not permission to test it with live records.

## Authentication and lifecycle

Use existing Supabase Auth, verify provider configuration and AAL2 support before choosing a login flow. The operator should independently confirm the intended person's existing verified account and enrolled MFA via authorized provider controls; never request passwords, keys, access tokens or MFA codes through chat. Owner-run bootstrap requires separate approval and records an event; the SQL cannot prove a human identity and does not itself check enrollment. The prototype requires AAL2 at every RPC but provides no login, MFA challenge, role assignment, session timeout, logout, recovery, invitation, user listing or protections against disabling the last super admin. These must be implemented and tested before deployment. Concurrent in-flight requests can complete after membership disablement due to transaction timing; disabling does not invalidate bearer tokens. A server-controlled session maximum, reauthentication policy and recovery process still need design and actual provider testing.

## Review/publish/rollback design gaps

Prototype state transition is draft → submitted → approved/rejected → published. Rejection is terminal; create another draft to revise. RPCs do not yet expose a safe read/list API, revision rollback or managed authoring of a historical version. Product rollback must create a *new draft* from a known previous revision, compare against the current live revision, go through independent review and explicit authorized publication, and audit both intent and result. Automatic reversal of arbitrary historical SQL or destructive schema rollback is unsafe. Define conflict handling across all public columns, enforce platform-specific limits (including LinkedIn headline separately), update derived fields, enforce uniqueness, and test on an isolated stack before defining migration-ready publish SQL. Public SEO and generated features require actual runtime/build integrations, not mere row changes.

## Threat analysis

- **Anonymous or normal user escalation / forged claims:** deny direct table access; validate JWT via platform and check `auth.uid()`, membership and AAL2 inside each database RPC. Test wrong issuer/audience/signature, revoked and expired tokens in a real gateway; local `auth.uid()` is a fixture, not proof of verification.
- **Compromised privileged account / stolen token:** least privilege, AAL2, short approved sessions, reauthentication for sensitive operations, independent reviewer and switch. AAL2 JWT alone doesn't guarantee recent MFA or resist replay; rate limits, session age, revocation and incident procedures remain unresolved.
- **Privilege escalation via definer functions:** schema-qualified names, fixed search path, input bounds and explicit grants, but actual function ownership is currently inherited from the migration executor; because real content tables are owned by `postgres` and RLS is not forced, owner permissions are high risk. Review a dedicated least-privilege owner, actual Supabase default grants and all functions before any migration.
- **Direct API or origin bypass:** Edge origin allowlist only controls browsers; direct PostgREST and public RPC calls remain possible. No secret in client; server/database authorization must stand alone.
- **CSRF/XSS/token leakage:** do not expose tokens in URLs/logs or HTML; choose a secure session architecture, CSP and dependency review; use non-cookie bearer requests with strict CORS and validate in real browsers. A browser bearer token remains vulnerable to XSS. No security review has yet verified these protections.
- **Audit tampering, omission, failed requests:** triggers prevent routine updates/deletes but privileged owners can alter or drop evidence. Successful changes log atomically; failed authorization attempts are not recorded by this SQL because exceptions roll back transactions. Separate privacy-preserving, access-controlled provider/security logging and independent retention require design and plan verification.
- **Stale writes / unsafe publish / concurrency:** row locks and a limited baseline comparison exist; full row coverage, per-platform validation, idempotency, pagination snapshots and load testing remain missing. Publishing stays off.
- **Guest data regression:** existing active-only RLS and privileges are untouched by prototype; definer bugs could nevertheless bypass RLS. Verify guest reads, no guest writes and guest UI/SEO after any separately approved change. Do not confuse frontend branch with data isolation.
- **Availability and data loss:** abuse/rate limits, timeouts, quotas, backups and restores must be tested. 099 destroys new audit/draft data; a rollback cannot unpublish content. Verify backup capability and restore in an independently authorized test environment, not the shared project.

## Isolation decision

Strict Preview/Production isolation requires an actually isolated backend: separate data, authentication, secrets, function deployments and administrative control boundaries, not just a Vercel Preview branch or different route. A separate Supabase project is one way, but the user has prohibited creating another project or duplicate database. A provider-supported isolated database branch might isolate database changes within the same project, but its actual Auth, Storage, function, secret and lifecycle isolation must be verified for the account and would still conflict with the current prohibition on a duplicate database unless the user revises it. No branch was created and entitlement is unverified. With the current shared backend and no independent isolated service, **strict isolation is not achievable**.

## Evidence and release gates

`npm run test:admin-draft` passes both local PGlite suites and a mocked gateway suite; `npm run typecheck` passes for the application. These tests cannot prove actual Supabase Auth, PostgREST, Edge JWT validation, MFA, network/CORS, live privileges or complete workflow correctness. No real admin account, HTTP session, Preview admin screen, production backup, live-content publication, mobile/desktop UI or field performance was tested. The local fixture temporarily turns the prototype switch on only inside its disposable database to exercise conflict/publish paths.

Do not approve or apply the prototype as the requested complete panel. Complete and review every missing module, implement accurate full-row validation and rollback, test in an authorized isolated environment, obtain an independent security review, and produce a final exact migration plus non-destructive recovery plan. Any shared deployment, bootstrap, permission changes or content publish must each be specifically approved. No current proposal authorizes those actions.
