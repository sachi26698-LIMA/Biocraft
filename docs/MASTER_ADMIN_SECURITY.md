# Security status

[Phase 4 security model and threat review](admin-backend-phase4/SECURITY.md) remain the baseline; update its permission matrix before activating any of the eight roles requested by the owner. The local 003 candidate seeds eight roles and a proposed permission catalog but assigns no users and grants no database or API capabilities. The mapping needs independent review and implementation of operation-, scope- and separation-specific enforcement. Browser state is not authorization. A server-side Supabase `getUser` boundary is implemented but not wired, deployed or tested against real Auth; no complete login, MFA, persistent session revocation, account lockout, trusted DB identity, permission functions or privileged APIs are implemented.

[Current shared-project review](MASTER_ADMIN_SHARED_PROJECT.md) supersedes the prior isolation decision. Local schema blocks anon/authenticated via revoked schema/table/function grants and restrictive RLS policies. Owner/superuser/BYPASSRLS can bypass RLS and modify grants/disable triggers. Append-only triggers are not independent audit storage. `admin_settings` and `details` JSON have no secret prevention or allowlists yet: never use as secret stores. Approval guards are integrity controls and cannot establish the caller's identity or permission. A reviewer UUID supplied to SQL does not authenticate that reviewer. No granting these commands to browser roles; do not deploy until provider, owner, role, identity, security, concurrency and audit review.

Live shared guest TRIGGER + TEMP privilege investigation and local reproduction are documented in [SQL review](admin-backend-phase4/SQL-REVIEW.md). No live exploit path was established, no grants/policies changed. Further investigation needs permission and proper scope; no dangerous live DDL tests.
