# Admin API contracts — design, not implemented

No API described below is currently deployed. No final SQL functions implementing these contracts exist yet. The earlier `admin-package/admin-gateway-DRAFT.ts` is a narrow mock-tested prototype and does not implement these contracts. Names and shapes here are a reviewable v1 target, not a representation of current functionality.

## Common contract

- Base: `/api/admin/v1` behind a Preview-specific server or Edge gateway. Verify JWT issuer, audience, signature, expiry and `aal2` with provider-supported verification, then resolve enabled membership and operation permission **inside the database transaction**. Browser role state and Origin are not authorization. Avoid service-role bypass in general endpoints. Disable privileged routes if the isolated backend configuration is missing or the request identity cannot be verified.
- All JSON requests must be `application/json`; responses include `Cache-Control: no-store`, correlation `request_id` and a request-scoped trace ID without credentials or payload. Errors: `{ "error": { "code": "FORBIDDEN|UNAUTHENTICATED|INVALID|NOT_FOUND|CONFLICT|RATE_LIMITED|UNAVAILABLE", "message": "safe message", "request_id": "uuid", "fields": [{"path":"content","code":"required"}] } }`. Use HTTP 401, 403, 400/422, 404, 409, 429, 503 respectively. No PII, SQL, stack, bearer tokens, email addresses or secret material in error responses/logs. Mask existence of unauthorized records.
- Paginated lists return `{ "items": [...], "next_cursor": "opaque string or null", "as_of": "RFC3339" }`; client asks `?limit=1..100&cursor=...`. Cursor is signed or server-validated, bound to a canonical filter/sort and contains unique `(sort_value,id)` tuple. Stable order is mandatory; time-dependent datasets can change while paging, so `as_of` is a boundary, not a claim of snapshot consistency. Exact count is optional, expensive and explicitly marked `count_kind: exact|estimated|unavailable`. Strict filter whitelists; no arbitrary column names, SQL, dynamic table names, sort directions or free-form metrics.
- State-changing requests require fresh authentication according to configured step-up policy, `Idempotency-Key` (UUID scoped to actor + operation and canonical request hash, bounded retention) and `If-Match` revision/version where applicable. Reject reuse of a key for different body with 409; persist result/operation and audit in the same transaction. Idempotency storage/migration remains **not designed in executable SQL**. Use server-maintained publish kill switch, initially off. A failed/denied operation emits a redacted provider security event outside the failed DB transaction, not a false transactional audit entry.
- Request size limit: 256 KiB JSON (bulk exports/imports require a separately authorized streaming job). Explicit server validation, field allowlists and canonical encoding, not trust in JSON/TypeScript type alone. No arbitrary executable HTML or untrusted script in previews. Admin URLs are noindex; isolate static bundle and avoid leaking data via cache, referrer or logs.

Roles: `S` Super Admin; `A` Admin; `E` Editor; `M` Moderator; `R` Analyst (retained from prior requirement). Each API checks a named permission; UI state is secondary. Editors cannot review their own work; moderators can flag/reject/submit review decisions but cannot approve publish or manage membership; only S/A publish other authors' approved changes. No last-super-admin lockout; role updates require recent step-up and protected audit. `R` gets approved aggregates only; no raw user/content administration unless separately authorized.

Platform, generator, category, collection, page/SEO, site setting, feature flag, font, emoji, symbol, hashtag and caption changes use the generic draft/review/publish endpoints with **separately typed, validated resource adapters**. No generic arbitrary table mutation endpoint. Moderator actions on user-generated reports or abuse require a real source and explicit event schema; no fake moderation queue. Hard-delete is not a default capability: archive/unpublish via reviewed revision; permanent deletion requires a separate authorized policy, data-retention check, backup and audit.

## Wire-level resource examples

- `bio` payload: `{ "id": "uuid-or-null", "title": "string-or-null", "content": "string", "plain_content": "string-or-null", "language": "en|hi|hg", "platform_id": "uuid-or-null", "category_id": "uuid-or-null", "source_slug": "string-or-null", "style_type": "string-or-null", "emoji_rich": false, "is_styled": false, "is_featured": false, "is_trending": false, "is_active": false }`. Server validates associations, expected base, Unicode normalization and consistent derived fields; `character_count` remains DB-generated and cannot be submitted. Multiple platform constraints and unscoped records must be explicitly defined; no inferred generic 150 limit. Defaults are not applied across languages or platforms.
- `category`: `{id,name,slug,description,platform_id,is_active,sort_order,seo:{title,description,canonical_url,robots}}`; publishing SEO requires its own `seo_pages` mapping and static-shell integration.
- `platform`: `{slug,bio_limit,counting_unit,enabled,tool_keys,template_version}`; eight allowed slugs exactly; user-facing limit semantics/Unicode count and public consumption require verification.
- `generator`: `{tool_key,platform_slug,languages,emoji_enabled,template_version,parameters}`; allowlist exact tool parameters; rule-based generator, no AI provider implied.
- `page` / `site_config`: typed section keys, approved text/media asset references and metadata; never arbitrary JS, untrusted markup, external URL or secret. Asset upload and malware/size validation are not yet specified.

## Mutation algorithm / integrity

All modifying adapters run one transaction: lock enabled membership and target/version records; verify current role and AAL/step-up, kill switch and approval rules; validate schema, canonical UTF-8 payload, allowed foreign keys, platform-specific constraints, generated fields and duplicates; lock/check current target snapshot/version; enforce idempotency; apply only allowlisted fields using static SQL; record before/after revision references and actor/reviewer/action in audit + publication history; commit atomically. Shared DB production publishes require separate explicit owner approval. Snapshot and hash cover **all relevant public fields and associated config**, not just the five-field prototype. For new rows, use stable preallocated UUID and uniqueness constraints; for archive, mark inactive without deleting history. Race/uniqueness error rolls back everything. For deployment/build-based SEO, transaction records an approved release; an authorized build/deploy job must report completion before saying published, and if it fails the prior build remains authoritative.

Database ownership must be least privilege and explicitly reviewed on real Supabase. `SECURITY DEFINER` with fixed `search_path`, schema-qualified names, no dynamic identifiers and narrow grants may still bypass RLS; verify function owner, role inheritance, default privileges and direct RPC invocation independently. The foundation SQL currently defines **none** of these v1 APIs. It adds no enabled endpoints.
