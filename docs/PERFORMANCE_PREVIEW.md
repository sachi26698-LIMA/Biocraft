# Preview performance investigation

These are **lab observations**, not Android field data or a 75th-percentile INP for the site. The reported 594.6 ms interaction cannot be attributed to a particular cause without its trace and interaction target.

**Measurement correction:** Later investigation found that this headless Chromium environment frequently does not produce paint/LCP entries until an explicit screenshot is taken. The earlier home LCP observations, including 6.15 s and 6.148 s below, and their FCP comparisons are screenshot-perturbed, not reliable browser or field LCP measurements. They should not be used to assert LCP progress or compliance. The new round below records this limitation and compares other observables as well.

## Method and limitations

- Compared the previous branch commit (`1974d11`) to the optimized branch in locally served Preview builds, without Supabase configuration. No network request to Supabase was measured.
- Chromium 141 headless, 390×844 emulated mobile viewport, touch emulation and DevTools 4× CPU throttling. The event timing comparison used local networking without network throttling. Timings fluctuate; the headless renderer and simulated input do not represent a physical Android device.
- Three repetitions of typing `love` into the boys collection search produced 12 reported interaction IDs in each build (Event Timing was configured with a 16 ms threshold). The nearest-rank sample 75th percentile of those **reported lab events**, not field INP, was 520 ms before and 56 ms after. In the events at those sample percentiles, input / processing / estimated presentation delays were approximately 0.4 / 4.6 / 515 ms before and 4 / 0.1 / 51.9 ms after. Event Timing rounds duration to 8 ms; events below the reporting threshold are absent. These are tiny samples, not a claim that the real-user 75th percentile meets 200 ms.
- Three clear-search taps had observed durations of 184–216 ms before and 40–48 ms after. Emoji filter taps were 176–392 ms before and 152–328 ms after. A fresh trace on the optimized collection included layout work as long as 709 ms (4× CPU); the large tasks still need investigation on actual devices.
- A separate local run emulated 100 ms network latency and about 1.6 Mbps download with 4× CPU throttling. Home-page LCP observations were 6.30 s, 6.15 s, 6.69 s, 8.25 s and 8.70 s at widths 360, 390, 430, 768 and 1440 px respectively; CLS was 0, 0, 0, 0.0010 and 0.0005. Initial long tasks remained, with maximums of 850, 909, 1004, 1061 and 1045 ms. Each is a single lab run, not a field percentile. No horizontal overflow was observed on the initial home viewport.
- At 390 px the browser exercised all eight platform switches and category-mode generation/regeneration, the three language controls on Instagram, the emoji switch, a font tool switch and previews, collection search/filter and the collection copy button. It did not check every interaction on every platform or a physical device. The repository's jsdom regression suite separately checks copy content and additional functionality.

## Changes

- Isolated the stage clock so its one-second timer no longer re-renders the illustration. Parallax animation frames stop when settled, and pointer geometry reads are coalesced before writes.
- Deferred collection and symbol search rendering, memoized their expensive result subtrees, and stabilized symbol-favourites snapshots and callbacks. Font/name galleries also defer transformations while preserving responsive input.
- Share only concurrent reads for the same collection. No data or failures are cached after completion, and retries remain fresh.
- On narrow screens, avoid backdrop blur on frequently visible surfaces and idle decorative animations, while retaining the palette and card designs. Existing reduced-motion behavior remains in place.

No collection virtualization was introduced: current seeded collections are comparatively small and virtualization could affect accessibility, copy-all and navigation. The later investigation below found a generation workload that justified a worker. Remaining work includes reducing large initial JS/layout tasks, measuring deployed Supabase request durations, and collecting real Android interaction traces and field data. Do not infer production performance from these local observations.


## Expanded audit: split routes and generation worker

Comparison: `ea42a75` versus the subsequent branch changes. Local Vite Preview builds, without configured Supabase, Chromium 141 headless on Linux. Network-throttled load experiments use a fresh browser, 390×844 touch/mobile emulation, 4× CPU, 100 ms latency and ~1.6 Mbps down; these are not Android Chrome or iOS Safari devices. Event Timing samples below use 4× CPU and local network without network throttling. Single-run route measurements and small samples have substantial noise; they cannot establish field p75, 60 FPS, or any target compliance. The user's 594.6 ms interaction is still unidentified and cannot be explained from these experiments.

- Lazily load non-default tool and page routes with reserved loading space; initial index JavaScript decreased from 867,240 to 405,197 bytes (gzip 257,017 to 126,676). This moves code into other chunks rather than eliminating all of it: for example, the remote bios chunk is about 230 kB uncompressed, and first navigation may require a download.
- Run bulk personal/category bio generation and single-card regeneration in a reusable worker when available. A synchronous fallback remains for unsupported/failed workers and can still block the main thread. Latest-wins cancellation ignores stale responses; controls provide busy feedback. Single-card generation now asks for one distinct item instead of generating a full batch. Worker cleanup and pending setting changes have regression tests.
- Serve a 871-pixel WebP derivative of the hero for narrower viewports; retain the full image for wide screens. Lazy-page fragment scrolling is restored after the target mounts; a real browser confirmed smooth scrolling completes (an immediate assertion was a test race).

### Coverage and remaining issues

- Local Chromium tested ten viewport widths 360, 375, 390, 430, 768, 820, 1024, 1280, 1440, 1920 for initial overflow/console errors and visited all tool routes at 390; separate 390 px interaction smoke covered all eight platform switches, category generation and regeneration, Instagram English/Hindi/Hinglish, emoji, fonts, collection filtering/copy click. WhatsApp and Snapchat status/caption tools were separately generated and regenerated in all three languages; their emoji toggles and copy buttons were clicked. LinkedIn headline/summary generation, regeneration and copy were exercised with `?platform=linkedin`. Copy clicks are not proof of device clipboard content. The generation test also started a real browser worker and verified results; cancellation, stale responses and worker failure were tested with mocked workers, and pending-setting changes in a component test. Full cross-product of platforms, settings and devices was not tested.
- Database read-only checks under the anonymous role returned 506 active visible records and two non-overlapping five-item RPC pages. Server-side `EXPLAIN ANALYZE` samples (not HTTP latency, under the management connection) measured a 30-row indexed source collection query at 0.201 ms execution and a five-row `dream` search at 17.646 ms execution; the search scanned the 506 rows and sorted matches. These are isolated snapshots, not an end-to-end DB response distribution or evidence of anonymous REST/CORS. Collection reads currently fetch up to 500 rows without pagination; RPC does not filter by source slug. Index/schema changes require approval and were not made in this performance round.
- Actual hosted Preview could not be reached from this sandbox: the connection closed before an HTTP response. Physical Android Chrome and iOS Safari, hosted screenshots, real Supabase network durations, field p75 and long-term memory are unverified. Screenshots from local emulation are not hosted or physical-device evidence. Previously disclosed migration `0004` was applied to the shared project without approval and remains in place; no further database changes have been made here. Obtain an explicit decision before any database reversal or production/main action.
- Dependency audit previously found Vite/esbuild development-tool vulnerabilities; a major upgrade requires separate compatibility evaluation. Continue to investigate initial rendering/layout, route-loading UX, slow-device fallback generation and DB scaling. No literal zero-latency claim is made.


## Follow-up round after `ec488e1`

Status: **not verified against the performance targets**. A real Android trace for the reported 594.6 ms event, physical-device testing, hosted Preview measurements, live browser-to-Supabase timing, and real-user field data were not available. A test request from this sandbox to Preview ended with `ERR_CONNECTION_CLOSED` before any HTTP response. Vercel deployment readiness is not evidence that the hosted app, RLS, CORS or device performance work end-to-end. The results below were obtained from local builds with Supabase unconfigured; no Production deployment, Production configuration, database schema, data, or RLS was changed in this round.

### Investigation and changes

- In a single 390 px 4× CPU timeline trace, the baseline homepage's hero used `useLayoutEffect` to synchronously read dimensions. Its longest React `FunctionCall` included a 671 ms whole-document layout with 1,074 dirty objects; the call lasted 915 ms. The same instrumented capture on the new version had a longest `FunctionCall` of 117 ms and longest layout of 451 ms. These nested timings overlap and must not be added. They identify **a** forced-layout bottleneck, not the cause of the earlier 594.6 ms field interaction. One trace per build is noisy and tracing changes timing.
- Changed the hero measurement to use `ResizeObserver`'s already-computed content rectangle instead of a forced pre-paint layout. The screen DOM persists across platform changes so resize observation continues. The interactive app-screen mock and default Bio panel are separately lazy loaded, with layout fallbacks; this shifts some work and network to first use, rather than making it disappear. Both still work when loaded. Touch-first devices no longer animate inherited hero colors or the glow/shadow on every frame; colors and interactive mock remain.
- A guarded, responsive hero preload runs only on the homepage, including when a static host serves the root shell as a clean-URL fallback. In the comparable local load runs the image request began around 125–184 ms instead of roughly 1,878–1,974 ms. Other routes did not request the hero. This is request discovery, not a verified field LCP result. Self-hosted Noto Sans Math was subset to the CSS's declared Unicode ranges: 270,516 → 84,460 bytes. FontTools verified that all 1,049 mapped codepoints retained identical outlines and horizontal metrics; the original and its license remain. No external font service was added.
- Use browser-native `content-visibility: auto` and remembered intrinsic sizes for offscreen home sections, footer and collection cards. The elements remain in the DOM; local tests scrolled to the final collection cards and clicked copy at 390, 820 and 1440 px. In one 390 px trace, collection longest layout fell from 700 to 262 ms. Individual cards may need rendering when first scrolled into view; long-scroll, assistive-technology and Safari behavior remain to be checked on devices. Estimates can also affect scrolling/CLS when content is first revealed.
- Bio generation still uses a reusable worker. When Worker creation fails or is unavailable, the same generator now yields in batches, with a roughly 5 ms slice budget and cancellation checkpoints instead of computing the entire fallback as one task. A 4× CPU local browser test with `Worker` disabled produced 16 valid bios for a deliberately constrained request for 20 and recorded no long task during that run; rendering and single operations can still block, and this is not a guarantee of zero blocking. Seeded regression tests verify the same algorithm/output in the worker/synchronous and incremental paths across modes, languages and emoji settings. Other generators remain synchronous and need further profiling; no claim that **all** generation can never block is justified.
- Successful empty Supabase collection responses are now treated as authoritative, rather than reviving stale bundled entries. Concurrent-only request deduplication and fresh retries remain. No speculative caching was added. The collection reader still caps a read at 500; replacing it with consistent multi-page retrieval needs a correctness design for concurrent changes and should not be presented as completed. The server RPC uses stable ordering from the previously disclosed migration; no DB changes were made in this round.
